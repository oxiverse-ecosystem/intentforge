ROOT CAUSE (file:line)
----------------------
1. semantic_relevance_score (gateway/src/main.rs:2337) = UNIGRAM cosine
   similarity on stemmed tokens. It only asks "do the query words appear in
   the result?", never "in the right sense?". "square"+"circle" present =>
   high score regardless of meaning. This IS the closest thing to a
   "plausibility monitor" the user referenced, and it has no word-sense
   discrimination. So it cannot catch the collisions above.

2. topic-coherence block (line 3788-3901) only checks DISTINCTIVE-TERM
   PRESENCE (substring). "Square (POS)" contains "square" => passes. No
   co-occurrence / phrase / sense check. So a wrong-sense match survives.

3. content_quality_score (line 964) only detects gibberish/spam (entropy,
   alpha ratio, avg word len, clickbait phrases). Natural-language but
   off-sense content (a dictionary def, a JS API page) scores high quality.
   So it cannot demote junk that is well-written but irrelevant.

4. No word-sense disambiguation anywhere: the intent engine emits
   constraints as bare tokens ("+square +circle"), and the gateway matches
   them as substrings. There is no sense/entity resolution (e.g. "square" the
   math verb vs "Square" the company; "promise" the moral noun vs the JS
   object; "crash" the program fault vs the dictionary verb).

Net: the "plausibility monitor" the user imagined does not exist. What exists
is keyword-overlap + spam filtering. That is exactly why these queries leak
junk.


WHY GRAVITY DOUBLED IS FINE BUT THE OTHERS AREN'T
-------------------------------------------------
"gravity doubled" has a distinctive, unambiguous term ("gravity"/"doubled")
with essentially one sense in search results, so substring presence == correct
sense. The failing queries all involve POLYSEMOUS words (square, circle,
promise, crash, perpetual motion) where a different sense also matches the
substring. The failure mode is specifically: polysemous-query + no sense
resolution.


PROPOSED FIXES (priority order; I did NOT implement — you asked to investigate)
-------------------------------------------------------------------------------
P-A (highest value, lowest risk): Boost results that contain the query's
    distinctive terms as a CO-OCCURRING PHRASE, not just individually.
    e.g. "square a circle" => require "square" within N words of "circle" in
    title/content, or require the geometry sense markers (impossible,
    construct, compass, π). For polysemous single-token queries, demote
    results whose only match is the wrong sense. This is data-driven (phrase
    proximity), no hardcoding of domains. Code: semantic_relevance_score
    (2337) + topic-coherence (3867).

P-B: Add a lightweight WORD-SENSE guard using the existing intent signal.
    The intent engine already knows intent (technical/how-to/moral...). For
    technical/how-to queries, prefer results from docs/StackOverflow/dev
    domains and penalize dictionary/encyclopedia/brand-POS pages that match
    only on a polysemous token. The dictionary-site penalty (3947) already
    exists — extend it to polysemous-sense collisions. Code: 3903-3973.

P-C (conspiracy/clickbait): For queries whose phrasing asserts a fringe claim
    ("government secret kept from the masses"), prefer authoritative/skeptical
    sources (encyclopedia, edu, established science outlets) and down-rank
    clickbait that echoes the claim. Needs a claim-frame detector (lexical:
    "secret kept from", "they don't want you to know", "what they hide") —
    bounded, not a full classifier. Code: topic-coherence / authority block.

P-D (honesty): When the top-K results have low best-sense-hits (as "square a
    circle" scored 0/17), surface a "low-confidence / no strong match" flag
    like the existing query_quality field, instead of presenting junk as
    authoritative. Fail-closed, honest UX.
